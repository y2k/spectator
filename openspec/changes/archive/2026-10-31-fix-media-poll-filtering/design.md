# Design

## Context

Мотивация описана в `proposal.md`. Изменение пересекает два модуля: `telegram/parse-posts` возвращает `{id, text}`, а `main/matches-selection-rule` решает, отправлять ли уведомление. Сейчас отсутствие текста даёт `true`. Парсер читает только `.js-message_text`, обрабатывает `br`, обрезает пробелы и декодирует сущности; неизвестная сущность превращает текст в `nil`.

Проверенная разметка `https://t.me/s/serbia/107367` содержит фотографию без `.js-message_text`. В `https://t.me/s/serbia/107388` вопрос «У вас есть счет в ALTA Banka?» доступен в `.tgme_widget_message_poll_question`, варианты — отдельно в `.tgme_widget_message_poll_option_text`. Текущий парсер оба поля игнорирует.

## Goals / Non-Goals

**Goals:**
- Сохранить интерфейс `{id, text}` и существующий путь проверки/продвижения курсора.
- Повторно использовать нормализацию текста и существующий matcher для вопроса опроса.
- Зафиксировать регрессии через существующие Worker-тесты и локальные HTML-фикстуры.

**Non-Goals:**
- OCR, анализ изображения, переход на другой Telegram API, изменение синтаксиса `/filter`, новое хранение типов публикаций.
- Фильтрация вариантов ответа, процентов голосов и реакций.

## Decisions

### Минимальное расширение существующего парсера

Добавить `.tgme_widget_message_poll_question` к источникам текста внутри `[data-post]`, применяя те же сбор текстовых фрагментов, обработку `br`, trim и decode-entities. Селекторы вариантов ответа и контейнера опроса целиком не добавлять. Не вставлять пробелы между произвольными потоковыми фрагментами текста: это могло бы разорвать слово или `C++` внутри форматирования.

Альтернативы: извлекать весь текст опроса проще концептуально, но противоречит выбранному пользователем ограничению «только вопрос»; отдельная модель данных опроса не нужна существующему matcher.

### Отсутствие текста не удовлетворяет настроенному правилу

В `matches-selection-rule` сначала сохранить безусловное совпадение при отсутствии Selection Rule. При наличии правила и пустом/отсутствующем тексте возвращать отказ; затем применять прежний алгоритм ключевых слов. Нормализация whitespace остаётся в парсере.

Выбран единый отказ для всех настроенных правил, включая правила только с запрещёнными словами. Предлагаемое техническое следствие: текст, ставший `nil` из-за неподдерживаемой сущности, также отклоняется. Это сохраняет имеющуюся модель данных и не вводит отдельную классификацию причин отсутствия текста.

Альтернативы: сохранить разрешение для пустого текста — воспроизводит исходную проблему; запретить все медиа и опросы — теряет публикации с доступной подписью/вопросом, которые удовлетворяют правилу.

### Курсор и совместимость

Использовать существующую ветку `update-cursor` для отказа. Не менять схему БД, курсоры и алгоритм обхода. Обновить `CONTEXT.md`, поскольку текущее определение прямо обещает противоположное поведение; в старом плане фильтрации пометить прежнее разрешение как заменённое, сохранив его исторический характер.

## Risks / Trade-offs

- Разметка Telegram Preview не является стабильным API → тестовая фикстура воспроизводит наблюдаемые классы вопроса и вариантов; сохраняется существующий `ponytail:` комментарий о границах поддержки.
- Полезный пост с недоступным текстом будет скрыт → это явный результат строгого фильтра; задача без Selection Rule продолжает принимать все посты.
- Фикстура `quiet/49` содержит `&copy;`, которое текущий decoder не поддерживает → изменить ожидаемое уведомление на отсутствие отправки и продвижение курсора; не расширять decoder в этом изменении.
- Текст соседних постов или вариантов может ошибочно попасть в вопрос → покрыть последовательные публикации и совпадения только в вариантах отдельными проверками.

## Migration Plan

После реализации выполнить `make test` и развернуть Worker обычным способом. Миграций данных нет; новые правила действуют только для публикаций после текущего курсора. Откат версии Worker восстанавливает прежний отбор будущих публикаций, но не переотправляет уже пропущенные публикации.
